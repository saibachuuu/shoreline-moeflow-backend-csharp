# Job handler side-effect audit and crash semantics (2026-11-11)

Scope: `src/Shoreline.Api/Jobs/*` (12 queue consumers) against their service bodies.
`JobQueueTests` only proves queue-state transitions (concurrent claim, lease expiry,
stale owner, 5 attempts) — it does **not** prove handler-level idempotency. This doc is
the blocking evidence for the Python → C# production replacement.

Queue contract (applies to every row below): at-least-once delivery. A job is
re-delivered after its 2-minute lease expires without renewal, and retried with
backoff `min(300s, 5 * 2^attempts)` until the attempt ceiling (`Jobs:MaxAttempts`,
default 5). There is no broker-level deduplication; every handler MUST converge on
replay. `JobWorker` claims only kinds present in its `IJobHandler` registry.

Python task names come from `docs/data-job-parity-audit-20261110.md` (baseline
`be0b717`); handler existence there does not imply retry/recovery acceptance.

## Queue/hardening deltas applied with this audit

- `Jobs:MaxAttempts` (default 5) replaces the hardcoded `5` in `ClaimAsync` terminal
  sweep and `FailAsync`; backoff stays `min(300s, 5 * 2^attempt)` — exponential,
  Celery-style, bounded, never infinite.
- `Jobs:WorkerEnabled = false` makes `JobWorker.ExecuteAsync` return immediately
  (API instance runs no consumer). `StoragePool:WorkerEnabled` semantics untouched.
- `JobWorker` graceful shutdown: stopping stops *claiming*; an in-flight handler
  keeps its own unlinked execution token so `ShutdownTimeout` (30 s, `Program.cs:17`)
  bounds completion instead of cancelling work mid-write; `Complete`/`Fail` use a
  bounded non-cancelled token so a finished job is never left `running` by shutdown;
  the lease is no longer renewed after shutdown starts, so an unfinished job
  expires naturally and is reclaimed.
- Structured worker logs carry `jobId/kind/attempt` only — never the payload.
- New `verification.sent` CAS in `SecurityEmailHandler` (fix for row 8).

## Residual risks (not closed by this change)

1. `output_team_projects` fan-out has no dedupe key — redelivery duplicates
   per-target output rows (row 3). Needs a team-run id or resume-from-existing.
2. Proofread post-flip redelivery duplicates depend on `DeliverAsync` claim
   semantics (row 7) — needs a dedicated notification-publish replay test.
3. Archive-import crash between entry upload and `AdvanceAsync` re-uploads one
   entry (row 10) — bounded orphan, but the uploader-overwrite path deserves a
   production-`FileService` replay test (current proof uses the fake uploader).
4. `team-create` replay safety bottoms out in `JoinTrustedAsync(request_id)`
   idempotency (row 9) — assumed, not re-proven here.
