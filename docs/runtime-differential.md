## What was compared

The test seeds every fixture document from `bson_base64` into the random
`LocalServices` database, then drops the fixture-owned collections before
inserting the fixture rows. The startup-seeded `language` and `team_role` rows
are removed so fixed fixture IDs and field order are authoritative. It verifies
the raw BSON digest before and after each request.

- All eight fixture request/status/body cases.
- Every JSON object field, array element, array order, and JSON value kind.
- `Content-Type` and `X-Pagination-*` response headers.
- Seed BSON byte digest, document counts, and before/after immutability.
- A synthetic C# `LegacyToken.Issue(ownerId, owner.p)` bearer, not the Python
  token. Token wire-format differences are outside this comparison.

Dates are normalized only when both values parse to the same UTC instant; a
format-only difference is recorded as `wire-format`, not treated as a business
match. No fields were dropped, no objects were truncated, and permission arrays
are compared in their original order.

## Production fixes

Only these five files were changed, within the review-approved scope:

1. `src/Shoreline.Api/Features/ApplicationService.cs`
   - `ScopeOf` accepts both singular and legacy plural group types:
     `"project" or "projects"` and `"team" or "teams"`.
   - Application payloads use Chinese source names when `Accept-Language` is
     absent. The reference runtime has no translation catalogs, so Python
     `gettext` returns the stored Chinese source strings. An explicit `en`
     header still selects the existing English view.
   - Application `group_roles` are ordered by descending role level to mirror
     Python's `TeamRole.system_role_data` order. Plain `_id` ordering put the
     beginner role first and did not match the reference payload.
2. `src/Shoreline.Api/Features/InvitationService.cs`
   - `FetchGroupAsync` accepts singular and plural team/project group types.
   - `PostInviteAsync` normalizes to the internal scope before `ParseRoleId`,
     avoiding a plural boundary value leaking into role validation.
3. `src/Shoreline.Api/Features/TeamEndpoints.cs`
   - Empty team-list `word` uses the exact legacy message
     `请求参数不能为空或没有需要的值`.
4. `src/Shoreline.Api/Infrastructure/Pagination.cs`
   - `From(HttpRequest)` keeps its existing signature and reads
     `Pagination:DefaultLimit` (deployment default 30) and
     `Pagination:MaxLimit` (default 100).
   - Invalid non-positive values fall back; page values below 1 become 1; a
     positive limit is capped; page overflow remains a 400 validation error.
   - The explicit-value overload remains available to endpoints with a
     different legacy default.
5. `src/Shoreline.Api/Features/TermEndpoints.cs`
   - `ParsePage` now delegates to `Pagination.From` instead of duplicating a
     hardcoded page parser. `TermService.LegacyDefaultPageLimit` was not
     changed.

No production avatar fallback was changed. The empty-avatar match comes from
the test's synthetic configuration equivalence.

## Compatibility HTTP regressions

`tests/Shoreline.Tests/RuntimeCompatibilityHttpTests.cs` adds six real HTTP
tests seeded from the same fixture:

- `ApplicationPluralRoutesAcceptTeamsAndProjects` (GET/POST for both plural
  routes, public info, and no membership side effect from applying);
- `InvitationPluralRoutesAcceptTeamsAndProjects` (GET/POST for both plural
  invitation routes);
- `UnknownGroupTypeReturnsLegacy5001`;
- `UnsupportedCollectionMethodsReturnMethodNotAllowed`;
- `PaginationUsesLegacyDefaultsCapsAndRejectsOverflow`;
- `PaginationHonorsTheSyntheticReferenceLimits`.

The invitation and application POSTs use a newly created external user rather
than the fixture owner, because the owner is already an active team member and
the legacy apply guard correctly rejects an already-joined applicant.

## Remaining differences (not production-fix candidates)

- ASP.NET emits `application/json; charset=utf-8`; Flask emits
  `application/json`.
- C# timestamps use six fractional digits; Python emits whole seconds. The
  parsed instants are identical.
- `GET /ping` is `text/plain` in ASP.NET versus `text/html` in Flask.
- `POST /ping` is an empty ASP.NET 405 response instead of Flask's HTML 405
  body and has no `Content-Type` header. Status 405 is still verified.

These are framework/wire-format differences and are reported separately. They
do not hide or normalize any business field.
